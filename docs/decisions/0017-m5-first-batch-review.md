# 0017 M5 首批评审

- 状态：已接受
- 日期：2026-09-11
- 阶段：M5 Reliable Provider Routing（目标版本 `v1.0`）
- 前置：[ADR 0016](0016-m5-scope-and-first-batch.md) 把首批收窄为显式切换与路由审计
- 结论：**首批的三个验收目标达成，但 M5 不关闭**，且首批留下一个与 M4 同型的缺陷

这是首批评审，不是里程碑收口。M5 的七条退出条件里，首批只触及三条。

## 1. 首批的三个验收目标

| 目标 | 结论 | 依据 |
| --- | --- | --- |
| 每次路由可解释且可审计 | **达成（有边界）** | `connect`/`switch`/`run` 共用的配置路径写 `selected`，含 grounds、`changePlanId`、`transactionId`、`catalogVersion`、凭据；`run` 与 `verify` 写 `attributed` 并回指仍在生效的那条决策。边界见第 3 节 |
| 切换失败不会破坏 Agent 配置 | **达成** | 三个失败点各注入一次（凭据签发、写入后验证、绑定保存），逐项断言文件内容、存储绑定与 Hub 仍持有的凭据回到切换前。**做了变异检查**：去掉回滚路径上的撤销，对应测试变红 |
| 用户始终能看到实际 Deployment 和计费主体 | **达成（有边界）** | `connect`/`switch` 输出 deployment id 与将被计费的 runtime credential；`verify --live` 按 requestId 精确归属；launcher 按时间窗归属。边界见第 3 节 |

现网验证：`connect` 写出 `selected/connect/explicit`，`verify --live` 写出 `attributed/verify/confirmed`（一次点名请求），第二次 `run` 的归属回指到同一条 `selected` 的 id。

## 2. 形状上的决定，事后看是否站得住

- **决策与代价是两条不可变记录，而不是一条被追写的记录。** 站得住：`verify` 的归属在决策之后数秒产生，launcher 的在数分钟后，两者都不可能在决策时知道。追写会毁掉审计唯一的用处——当时相信的是什么；
- **`unconfirmed` 单独成一档。** 站得住：现网确实出现过台账尚未结算的情形，把它写成「确认花了 0」会让一条本该引起注意的记录看起来正常；
- **写审计失败不回滚已发生的路由。** 站得住，但代价要写明：**日志因此可能有洞**，只以警告提示。审计的完整性在这里让位给了「不破坏已应用的状态」，这是有意的取舍，不是疏忽。

## 3. 首批**没有**做到的

- **`grounds: "recommendation"` 是一个没有任何代码写入的字段。** schema 定义了它，`recommend` 与 `connect` 之间却没有传递 Recommendation id 的通路，因此「这条路由是一次排序的结果」——最值得审计的那种依据——今天无法产生。

  **这与 M4 的 `scenarioId` 是同一个错误**：[ADR 0013](0013-m4-second-review.md) 之前刚记过「声明了却无人读写的字段」，本批隔一个工作段又造了一个。区别只是这次是在写它的当天发现的。修法明确：`recommend` 输出的 `rec.sha256.<hash>` 需要能被 `connect` 接受并记入审计；

- **`restore` 不写审计。** 一次恢复会把连接目标改回去，那同样是一次「连接目标的确定」，按首批自己的定义就该记。现在不记，于是日志里会出现「切到 B」之后凭空回到 A 的空档；

- **没有任何命令能读这份日志。** 文件在 `~/.local/state/apexnova-connect/audit/routing.jsonl`，只能手工 `cat`。**没人能读的审计只是文件**，退出条件要的是可解释；

- **launcher 的归属是时间窗，不是精确匹配。** `verify` 按 requestId 精确，launcher 只能按小时桶做前后差。同一账号在别处并发使用时，差值会把别人的请求算进来。`mismatched` 因此可能误报；

- **失败注入只覆盖 `switch`。** `connect` 与 `run` 的配置路径与它共用同一个函数，因此大概率同样安全，但「大概率」不是证据。

## 4. 是否有真实用户完成核心流程

与 M4 收口时相同：**没有外部用户**。首批的现网验证全部由维护者完成。审计记录至今**没有被任何人用于回答一个真实问题**——它被写出来、被读回来断言过，但没有人拿它查过一次「上周那次调用为什么用的是这个模型」。这是它是否有用的唯一检验，尚未发生。

## 5. 下一批应当是什么

按影响排序，前三条都来自第 3 节：

1. **`recommend → connect` 的 Recommendation 传递**，让 `grounds: "recommendation"` 不再是死字段。它同时补上 M4 收口时点名的另一条：推荐与连接之间没有闭环；
2. **`restore` 写审计**，补上日志的空档；
3. **一条读取审计的命令**，否则可解释性只存在于文件里；
4. 之后才是 Gateway 那条线（[ADR 0016](0016-m5-scope-and-first-batch.md) 决策 2 已说明为何它不与审计同批）。

**不建议**在上面三条完成前动 Gateway：首批刚证明了一件事——审计的价值取决于它能否回答「为什么」，而今天最有价值的那个「为什么」（来自排序）恰恰还写不进去。

## 6. 是否需要缩小而不是扩大范围

保持收窄。首批的四项产出（schema、包、两处写入、失败注入）已经暴露出三个本可以在设计时想到的缺口，其中一个还是刚批评过的同类错误。这说明**收窄的尺度仍然偏大而不是偏小**。
