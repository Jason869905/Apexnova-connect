# 0030 运行时凭据的有效期可配置，续期窗口随之按比例缩放

- 状态：已接受
- 日期：2026-09-13
- 阶段：M5 Reliable Provider Routing（目标版本 `v1.0`）
- 前置：[ADR 0029](0029-launch-must-honour-the-configured-file.md) 第 6 节指出 [ADR 0020](0020-gateway-batch-closure.md) 的条件 1 今天**无法达成**，因为 TTL 固定 24 小时
- 结论：新增 `--credential-ttl <秒>`（120～86400，默认 86400）；续期窗口改为「最后一小时或寿命的后一半，取较短者」

## 1. 为什么这不是「为了测试而改产品」

需要先自问一次，因为本项目否决过这种做法（[ADR 0012](0012-region-is-the-wrong-requirement.md)、[ADR 0022](0022-m5-midpoint-review.md)）。

**这条改动有独立于测试的理由：一次十分钟的运行不需要一枚 24 小时的凭据。** `run --gateway` 在结束时会取回自己的凭据；**万一它没走到那一步**（进程被杀、机器断电），留下的是一枚还能用一天的凭据。[ADR 0021](0021-gateway-credential-renewal.md) 第 2 节已经用同一个理由把 `--gateway` 改成一律签发短期凭据——本记录只是把「短」交给使用者决定。

顺带解决的才是可测试性：**一条只有等满 23 小时才走得到的代码，实际上没有人会去验证它。** [ADR 0019](0019-gateway-first-slice-review.md) 把凭据续期列为缺口，[ADR 0020](0020-gateway-batch-closure.md) 把它改判为「未实现」，[ADR 0021](0021-gateway-credential-renewal.md) 实现了它——**三份记录、两天，没有一次真跑过那条路径**，因为跑一次要一天。这本身就是设计问题。

## 2. 固定一小时的窗口，一旦寿命可配就立刻错了

原来的规则是「剩余不足 1 小时就续期」。这在每枚凭据都活 24 小时时没有问题。

**寿命一变就崩**：一枚十分钟的凭据从签发那一刻起就「剩余不足 1 小时」，于是**每个请求都会触发一次续期**，而每枚替换件同样立刻到期——[ADR 0021](0021-gateway-credential-renewal.md) 花力气做的 single-flight 与冷却挡不住这个，它们防的是并发与失败，不是这种自我循环。

新规则：**最后一小时，或寿命的后一半，取较短者。**

- 24 小时凭据：`min(1h, 12h)` = 1 小时——**与原行为完全一致**；
- 10 分钟凭据：`min(1h, 5min)` = 5 分钟——在半程续期，替换件再活 10 分钟。

为此绑定里要记 `issuedAt`（存储格式 v4）。没有它就算不出寿命，只能拿 `expiresAt` 和当下比。**v4 之前写的绑定没有这个字段，一律退回固定一小时**——而对 24 小时凭据来说，那正是减半规则给出的同一个答案，所以旧绑定的行为一个字节都不会变。**不给它们编一个 `issuedAt`**：编出来的签发时刻就是编出来的寿命，会悄悄改变续期时机。

## 3. 续期要复制原来的寿命

`runtimeCredentialForLaunch` 原先硬编码 `expiresIn: 86_400`。若不改，一次 `--credential-ttl 120` 的运行会在第一次续期时拿到一枚 24 小时凭据——**命令做出的选择被悄悄撤销**。现在续期按当前绑定的实际寿命签发。

同一处还有一个连带缺陷：续期后的校验是 `到期时间 - 现在 <= 固定一小时就报错`。短寿命下，**Hub 发回的每一枚合格替换件都会被判为「寿命不足」**。改为按同一个缩放窗口比较。

## 4. 边界

下限 120 秒，上限 86400 秒。

下限不是随手定的：窗口是寿命的一半，低于两分钟意味着替换件刚到手就又该换了，运行会把自己耗在签发凭据上。上限是 Hub 现有的运行时凭据上限，也是原默认值。

三处改动各有变异验证：去掉缩放窗口、把续期改回 86400、把选项忽略掉——每一种都会让测试失败。

## 5. 真机验证：条件 1 达成，途中抓到三个缺陷

有了可配的寿命，[ADR 0020](0020-gateway-batch-closure.md) 的条件 1 第一次可以在几分钟内走到。做法是 `--credential-ttl 120` 配一个需要三十次顺序工具调用的任务。

**第一次尝试失败了，而且是真的失败**：运行 3 分 13 秒，读完三十个文件之后 Agent 死于 `Invalid API key`。计费台账显示这次运行只用了两枚凭据（11 + 20 个请求），而 120 秒寿命、60 秒窗口的运行在 190 秒里本该续期约三次。

**ADR 0020 第 2 节当时写「我们已经知道它会失败，不知道的只是失败的形状」。形状现在有了，而且它不是当时猜的那个**——不是凭据到期后 401 被忠实转发这么体面，是 Agent 拿到一句 `Invalid API key` 然后死掉，而命令没有给出任何解释。

三个缺陷，按发现顺序：

### 5.1 失败时，唯一能解释失败的信息被丢掉了

Gateway 的运行期通知（凭据续期了、或者续期失败了）原先只在启动成功之后才被收集。Agent 非零退出时它们被直接丢弃——**恰好丢在它们唯一有用的那一刻**。先修了这个，否则查不下去。

### 5.2 运行期续期继承了整条命令的截止时间

修完 5.1 之后，原因一句话就出来了：

> `The runtime credential could not be renewed mid-run (Timed out waiting for another credential rotation to finish.)`

而锁目录是空的——**没有任何另一个轮换**。真正的原因是 `operationSignal`：它是**整条命令共用的一个截止时间**（默认 120 秒），在 `parsed` 上记忆化。一次三分钟的 `run`，跑到第二次续期时这个信号早已 abort，于是轮换锁的循环第一轮就抛错。

**结论很刺眼：任何比 `--timeout` 更长的 `--gateway` 运行都无法续期——而那正是唯一需要续期的那一类运行。** 这个缺陷把 [ADR 0021](0021-gateway-credential-renewal.md) 实现的整条路径变成了只在短运行上有效，也就是只在用不到它的时候有效。

代码里早有同形的先例与正确做法：`compensationSignal` 存在的理由就是「补偿性工作不得继承已经过期的操作截止时间，否则超时会泄漏凭据」。运行期续期是同一类——它发生在 Agent 运行期间，不属于命令自身的那串操作。新增 `inFlightSignal`，每次尝试取一个新的截止时间。

### 5.3 锁超时的消息指向了一个不存在的进程

`CREDENTIAL_ROTATION_BUSY` 原先无条件报「在等另一个凭据轮换结束」。而上面这次**根本没有竞争**，锁一次都没被别人持有过。这条消息会把人送去找一个不存在的并发进程。

现在只有真的撞见过被持有的锁才这么说；否则如实说「本次操作的截止时间在轮换开始前就已过去，没有别人持锁」。

### 5.4 同一个根因还藏在计费对账里

修完之后运行成功了，但输出里多了一句 `The billing ledger could not be read after the run`。运行结束后读台账用的也是那个早已过期的 `operationSignal`——**于是长会话的归属被静默丢掉，而那恰恰是最需要对账的一类运行**。同样改用 `inFlightSignal`。

### 5.5 最终结果

| | 值 |
| --- | --- |
| 运行时长 | **3 分 19 秒** |
| 凭据寿命 | 120 秒 |
| 续期次数 | **2 次，均成功** |
| 请求数 | **32**，经 Gateway 逐个记录 |
| 计费拆分 | 11 / 11 / 10，分属三枚凭据 |
| Agent | 退出 0，三十个文件全部答对 |

**这次运行活过了它起始凭据整整一倍多的时间。** 审计里那行 `32 requests — 11 on …pmbd4pri, 11 on …yx89z6df, 10 on …sxumk8j7` 是 [ADR 0021](0021-gateway-credential-renewal.md)「归属按凭据拆分」那条设计第一次在真实运行上兑现——在此之前它只有构造出来的证据。

**[ADR 0020](0020-gateway-batch-closure.md) 的条件 1 达成。**

## 6. 一条环境记录

第一次尝试是放在后台跑的，结果十一分钟里**一个请求都没有发出**（台账为零）——OpenCode 在没有 TTY 的环境里卡住不动。改到前台即正常。

杀掉那个卡住的 Agent 顺便在真机上验证了 [ADR 0029](0029-launch-must-honour-the-configured-file.md) 第 4 节的修复：Agent 非零退出后，网关端口立刻释放、配置被取回。修复之前，这一步会让进程永远挂着。
