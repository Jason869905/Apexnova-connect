# 0011 M4 里程碑评审

- 状态：已接受
- 日期：2026-09-10
- 阶段：M4 Match Beta（目标版本 `v0.4`）
- 结论：**不关闭**。四条退出条件满足三条，第三条（约束）有两个半项依赖 Hub 尚未发布的目录数据
- 后续：其中「区域」一项已按 [ADR 0012](0012-region-is-the-wrong-requirement.md) 从退出条件中移除（2026-09-11）——理由是那条要求选错了对象，不是做不到。本记录是 9 月 10 日那个时点的判断，不因此改写；**不关闭的结论不变**

本记录按路线图要求的五个问题回答。它是 2026-09-10 这个时点的判断，不预判 Hub 交付 12I/12J 之后的结论——那时另写收口记录，做法同 [ADR 0005](0005-m3-milestone-review.md) → [ADR 0006](0006-m3-closure.md)。

## 1. 退出条件是否全部满足

| 退出条件 | 结论 | 依据 |
| --- | --- | --- |
| 相同输入和规则版本产生可重复结果 | **满足** | 排序确定（同分按 `deploymentId` 字典序兜底）；契约测试对同一输入正反两次跑并断言逐字节相同；发布文档内容寻址为 `rec.sha256.<hash>`，同一份排行算两次是同一个 id。`catalogVersion`、`ruleVersion`、`profileVersion` 与逐项 `evidenceRefs` 全部记录在案（`profileVersion` 由 [ADR 0009](0009-recommendation-schema-carries-the-profile-version.md) 补上，schema 提到 0.2） |
| 每个推荐都有分项理由、备选和排除原因 | **满足** | 每个候选给出分项、分数、权重、依据文字与所引用 Evidence ID；被排除者逐条给出理由；零候选时报出最大的一组排除理由及计数 |
| 用户可以强制模型白名单、预算、区域和隐私约束 | **未满足** | 见下表 |
| 不存在隐藏商业评分项 | **满足** | `sponsored` 恒为 `false` 且不是打分函数的输入，由断言测试保证——不是承诺，是「没有东西可藏」 |

第三条逐项（详见 [ADR 0010](0010-m4-constraint-exit-condition-status.md)）：

| 分项 | 状态 | 阻塞在哪 |
| --- | --- | --- |
| 模型白名单 | 已实现 | — |
| 预算 | 已实现，**但产品上不可用** | 目录对全部 Deployment 发布 `pricing: 0`（需求 12H）。价格未知者在设了上限时判为不通过，因此**只要设 `--max-price`，本轮就没有候选** |
| 区域 | 不可实现 | 目录里没有任何区域字段（需求 12I） |
| 隐私 | 一半已实现 | 模型发布方目录给了（`--exclude-publisher`）；**实际运行请求的运营方不给**（需求 12J） |

**因此 M4 不关闭。** 按路线图原则，退出条件未满足时不得靠削减要求进入下一阶段；[ADR 0010](0010-m4-constraint-exit-condition-status.md) 决策 4 也已预先写死：若收口时仍无数据，如实记为未满足，不降低要求。这里执行的就是那条。

## 2. 哪些风险被验证或推翻

**被验证的：**

- **「先本地、后 Hub」是对的**（[ADR 0007](0007-m4-scope-and-recommendation-path.md) 决策 7）。M4 全程没有被 Hub 阻塞，而给 Hub 的三条需求（12H、12I、12J）是由真实产出反推出来的，不是凭空设计的契约。M3 验证过一次，M4 是第二次；
- **收窄到一个 Scenario 是对的**。首批闭环跑通之后暴露出的问题——身份、schema 一致性、约束语义——每一个都与 Scenario 的数量无关。多做两个 Scenario 只会把同样的缺陷复制三份；
- **「不给未测量分项默认分」这条规则扛住了压力**。它带来的后果是显眼的：今天的排序只由 `compatibility` 与 `context` 决定，输出上有五行「Not measured」。规则没有被这份难看的输出反过来修改。

**被推翻的：**

- **「目录声明可以当数据用」再次被证伪**，而且这次是价格。M3 时是能力声明（4 个 Deployment 都声明 `structured-output.json`，实测全不通过），M4 时是 `pricing: 0`。两次的形状相同：**一个发布出来的值，比一个缺失的字段更危险**——缺失只能猜，错误的值会被当真；
- **「实现与冻结的 schema 自然会一致」被证伪**。`recommend` 的输出多了三个候选字段与两个顶层字段、少了 schema 必填的 `expiresAt`，而**没有任何代码校验过**。Evidence 那条有 ajv 把关，Recommendation 这条没有，差别就是有没有人写那一行。

**新暴露的风险（此前没被识别）：**

- **同一条规则被写在多处，就会有多处漏掉同一个字段。** subject 身份曾有三份拷贝，platform 与 `scenarioId` 各漏在不同的拷贝里。已收敛为 `subjectIdentity` 一处；
- **一个静默生效为空的约束，比没有实现的约束更糟。** `--max-price` 曾对全部候选无效且不作声，显示的却是「已按预算筛过」。这与 M3 守的「不得把未测试显示成支持」是同一条规则的另一面，此前没被识别为同一件事。

## 3. 是否有真实用户完成核心流程

**没有外部用户。** 全部运行由维护者在 `testpro@test.com` 这个账号上完成，两个平台（`linux-x64` 与 `windows-x64`）都跑通了完整的 `recommend`，引用的是各自平台的真实 Evidence。

有两点必须写明，否则「跑通了」会被读成比事实更强：

- **没有人用这份推荐真的去连过一次 Provider。** `recommend` 的产出至今没有被喂给 `connect`——从推荐到连接这一步没有闭环，也没有人验证过排第一的那个 Deployment 用起来确实更好；
- **预算这条路径从未产出过一次有用的推荐**，因为设了 `--max-price` 就没有候选（12H）。它的正确性由测试保证，可用性没有被任何真实使用检验过。

## 4. 下一阶段的最大未决依赖

按影响排序：

1. **12H（目录价格）。** 它同时卡住两件事：`cost` 分项和预算约束。在它修好之前，M4 那条「预算」退出条件即使代码正确也无法验收；
2. **12I（区域）与 12J（运营方身份）。** 直接决定第三条退出条件能否满足。两者都不是 Connect 侧能补的，也都已明确写给 Hub；
3. **macOS 无实机。** 自 M2 挂到现在，M3、M4 都没有等它。`recommend` 在该平台如实返回无证据，但三平台验收这条 M2 退出条件仍然是欠着的；
4. **Scenario Quality Pack。** 路线图给 M4 的五个权重分项里，`quality`、`速度(latency)`、`隐私(privacy)`、`稳定性(availability)` 四个都没有度量来源，唯一有来源的 `cost` 又被 12H 卡住。**也就是说这五个分项今天没有一个在产生排序影响。**实际排序由 `compatibility` 与 `context` 承担，而这两个都不在路线图给 M4 的那份列表里。这不是缺陷，是一份需要正视的事实：M4 交付的是一个可解释、可复算、诚实的排序框架，而不是路线图当初设想的那套多维打分。

## 5. 是否需要缩小而不是扩大范围

**继续保持收窄，并且不为了关闭 M4 而扩大。**

具体主张三条：

- **不要为了让「权重」这条范围看起来完整而引入 quality 或 latency 的近似度量。** 没有可重复评分方法之前，质量分只会是一个看起来精确的意见（[ADR 0007](0007-m4-scope-and-recommendation-path.md) 已否决过一次，此处重申）；
- **不要为了满足第三条退出条件而自造区域或运营方数据。** 用 `baseUrl` 或实现指纹去推断区域，会得到一个看起来精确的错误答案，比没有约束更危险；
- **下一件值得做的事不是新分项，是把推荐接到 `connect` 上**——让「推荐 → 连接 → 验证」跑通一次。第 3 节写明了这一步至今没有闭环，而它比任何一个新分项都更能检验这套排序是否有用。

## 关闭 M4 需要发生什么

三条，全部可核对：

1. Hub 交付 12I（区域）与 12J（数据处理方约束的任一形状），Connect 据此实现区域与隐私约束并实测；
2. Hub 交付 12H（真实价格），使预算约束在产品上可用——代码无需改动，非零价格会自动重新参与排序；
3. 重新评审第三条退出条件，与其余三条一并记入收口记录。

若 Hub 在合理时间内无法交付 12I/12J，届时的选项是**按 [ADR 0008](0008-non-apexnova-candidates-belong-to-m5.md) 的方式把区域与运营方隐私移到 M5**，理由必须是结构性的（它们与 M5 的路由约束是同一件事），而不是「M4 拖太久了」。**那将是这条要求第二次被移动，因此需要比 ADR 0008 更强的理由，而不是更弱的。**
