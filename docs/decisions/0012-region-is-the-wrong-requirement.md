# 0012 区域不是一条约束，是一个测量条件

- 状态：已接受
- 日期：2026-09-11
- 阶段：M4 Match Beta（目标版本 `v0.4`）
- 影响：M4 退出条件去掉「区域」；需求 12I 撤回；[ADR 0011](0011-m4-milestone-review.md) 的相应结论按本记录更新

## 背景

路线图给 M4 的退出条件之一是「用户可以强制模型白名单、预算、**区域**和隐私约束」。[ADR 0010](0010-m4-constraint-exit-condition-status.md) 核对后记为不可实现（目录里没有任何区域字段），[需求 12I](../apexnova-ai-hub-requirements.md) 据此请 Hub 发布一个可比较的区域标识，[ADR 0011](0011-m4-milestone-review.md) 也据此判定 M4 不关闭。

这三步都建立在同一个未经检验的前提上：**区域是用户需要的那个东西**。本记录检验这个前提，结论是它不成立。

## 决策

**「区域」从 M4 退出条件中移除，需求 12I 撤回。** 这不是推迟，也不是降低要求——是这条要求本身选错了对象。

理由三条：

1. **用户想从「区域」得到的，是另外两样东西中的一样。** 要么是**低延迟**，要么是**数据落在某个司法辖区**。前者可以直接测量（Operational Evidence 的首 Token 延迟与端到端时长），后者正是[需求 12J](../apexnova-ai-hub-requirements.md) 要求的数据处理属性。两样都有比区域更直接的表达方式，中间那个标签不增加任何信息。

2. **它会是第三个被当成数据用的目录声明。** 区域标识无法被 Connect 校验——我们不可能验证一个 Deployment 真的在它声称的区域。这个项目已经被目录声明坑过两次，形状完全一样：M3 时 4 个 Deployment 都声明 `structured-output.json` 而实测全不通过；M4 时公共目录对全部 46 个 Deployment 发布 `pricing: 0`（需求 12H）。把一个同样不可校验的标签引进硬约束，是明知故犯的第三次。

3. **今天的产品形态里它没有可选项。** 46 个 Deployment 共用一个 host、一个 `kind: "platform"` 的 Provider，用户不选区域，Hub 路由。即使 Hub 发布了区域字段，它在推荐里也只能用来解释，不能用来选择。

**区域保留一个位置：测量条件。** 一条延迟证据必须记下客户端在哪测的，否则两个数字不可比。`compatibility-evidence.md` 的 Operational 一节已按此写明——它描述测量在哪做的，不是 Deployment 的属性。

## 后果

- M4 的约束退出条件从四项变三项：模型白名单、预算、隐私。三项都已有明确状态（[ADR 0010](0010-m4-constraint-exit-condition-status.md)、[ADR 0011](0011-m4-milestone-review.md)）；
- **隐私的分量因此变重。** 原本想通过「区域」表达的合规诉求，现在只能由 12J 承载。12J 从「一条需求」变成「该条退出条件能否满足的唯一外部依赖」；
- M4 仍然不关闭。去掉区域并没有让第三条退出条件成立：预算受 12H 所限在产品上不可用，隐私的运营方那一半仍然依赖 12J。**本记录不改变 ADR 0011 的结论，只改变其中一行的理由**；
- M5 的范围里写着「Deployment 健康、余额、区域和价格约束」。同一条理由适用，但 M5 尚未规划，本记录不单方面改动它——在 M5 规划时按本记录重新评估，路线图已就地标注。

## 被否决的选项

- **保留区域，等 Hub 发布。** 那会让一条选错了对象的要求继续挂在退出条件上，并且在 Hub 真的交付之后，我们会实现一个不可校验、且用户无从选择的过滤器。**满足一条错的要求不会让它变对。**
- **把区域降级为「展示用」而不是约束。** 听起来温和，实际是把一个不可校验的标签放进用户会据以决策的界面，并且不承担校验责任。不展示比展示一个我们不打算负责的字段更诚实。
- **用 `baseUrl` 或实现指纹推断区域。** 现网 85 个协议入口共用一个 host，指纹只保证「实现变了」、不承载位置。推断出来的区域会是一个看起来精确的错误答案，比没有约束更危险。
