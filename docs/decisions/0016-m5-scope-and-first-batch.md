# 0016 M5 启动：首批收窄为显式切换与路由审计

- 状态：已接受
- 日期：2026-09-11
- 阶段：M5 Reliable Provider Routing（目标版本 `v1.0`）
- 前置：[ADR 0015](0015-m4-closure.md) 关闭 M4

## 背景

M5 的范围表列了八项：Connection Profile 与显式 Provider 切换、Deployment 健康／余额／区域／价格约束、本地 Gateway 与 Hub 路由协作、Circuit Breaker、新请求边界上的受控选择、路由审计与实际计费来源、非 Apexnova 端点的证据采集路径、Pro 与 Team 能力。退出条件七条，其中两条是从 M4 移入的。

M3 与 M4 各自用一次收窄换来了可闭环的首批，两次的结论相同：**规模会先于结论成为瓶颈**。M4 更给出了一个具体尺度——一个分项从「有数据」到「进入排序」，需要解析、零值语义、有效期、约束语义，外加一次真实闭环才暴露得出来的错配。八项一起铺开不会比那更便宜。

同时，M4 收口时已有三样东西现成可用，它们恰好落在同一条线上：`switch` 已现网实测（含恢复时重新签发的凭据真实可用）；按 `requestId` 的逐条对账自 M3 起就在用；launcher 的归属对账已经能正面确认「请求落在我们签发的凭据与配置的 Deployment 上」。

## 决策

1. **首批只做两件：显式 Provider 切换，和路由审计。** 其余六项留待首批闭环跑通之后再排。

2. **首批不含 Gateway、Circuit Breaker、受控选择、Team。** 它们都要求一个「Connect 参与请求路径」的形态，而今天 Connect 只写配置、签发凭据、启动进程，请求由 Agent 直接发往 Hub。引入请求路径是 M5 最大的一次形态变化，不应与审计语义同时进行——否则出问题时分不清是路由错了还是审计错了。

3. **「路由」在首批的定义要写死，否则审计无从验收。** 今天没有 Gateway，一次「路由」就是**一次连接目标的确定**：`connect` 选定 Deployment、`switch` 更换 Deployment、launcher 启动时绑定哪一枚凭据。审计要回答的是三句话——**选了哪个 Deployment、依据是什么、实际由谁计费**。前两句来自 Plan 与 Recommendation，第三句来自台账。

4. **审计记录落盘，并且可追溯到已有的不可变对象。** 每次连接目标的确定写一条审计记录，引用已经存在的东西而不是另造一套：Plan/事务 id、Recommendation 的 `rec.sha256.<hash>`（若该次选择来自推荐）、`catalogVersion`、以及事后对账得到的 `requestId` 与 `apiKeyId`。**不得只写「切到了 X」**——那是结果，不是可审计的依据。

5. **非 Apexnova 候选来源与隐私约束不进首批。** 这是产品判断，本记录照记。但两者都是 M5 的退出条件，且 [ADR 0008](0008-non-apexnova-candidates-belong-to-m5.md) 与 [ADR 0014](0014-data-handling-attributes-belong-to-m5.md) 在移入时都写明推迟理由已经用掉：

   **因此「不进首批」不等于「不做」。** M5 收口时若两者仍未交付，按这两份记录的约定如实记为未满足，M5 不得凭它们关闭。要真正取消，需要的是第三次决定，理由必须是结构性的——像 [ADR 0012](0012-region-is-the-wrong-requirement.md) 对区域那样证明它选错了对象，而不是「来不及」。本记录不做那个决定。

6. **首批不依赖 Hub 新交付。** 切换与台账都已具备。M3、M4 两次都验证过「先本地、后 Hub」，给 Hub 的需求要由真实产出反推。

## 首批的验收目标

对应退出条件中首批能触及的三条：

| 退出条件 | 首批如何验收 |
| --- | --- |
| 每次路由可解释且可审计 | 每次连接目标确定都有一条审计记录，含依据与事后对账；同一次可由记录复算出「为什么是它」 |
| 切换失败不会破坏 Agent 配置 | 已有事务与逆序 `restore` 承担；首批补上失败注入下的验收，而不是只靠成功路径 |
| 用户始终能看到实际 Deployment 和计费主体 | launcher 的归属对账已做到一半（`run`）；首批扩到 `connect`/`switch`/`verify`，并把「实际计费主体」写进审计记录 |

**不在首批验收**：Provider 故障不自动重放（需要请求路径）、三个首批 Integration 达到 stable、以及上面第 5 条的两条。

## 后果

- 首批交付形状是审计记录的定义与落盘，加 `switch` 在失败注入下的验收，不新增请求路径；
- 审计记录一旦落盘就是对外语义，**其 schema 需要与 M0 的对象保持一致**，不得重演 M4 那次「实现与冻结 schema 漂移且无人校验」；
- M5 的退出条件仍是七条，本记录只决定首批做哪几条；
- macOS 仍无实机，自 M2 挂到现在，不在首批范围内解决。

## 被否决的选项

- **首批就做本地 Gateway。** 它是 M5 的核心，但引入请求路径的同时定义审计语义，会让第一次出问题时无法区分路由缺陷与审计缺陷。先把「说清楚发生了什么」做对，再去改变「实际发生什么」。
- **把非 Apexnova 与隐私两条退出条件就地删除。** 那是把要求改到现状上，[ADR 0012](0012-region-is-the-wrong-requirement.md) 与 [ADR 0014](0014-data-handling-attributes-belong-to-m5.md) 都否决过同一种做法。不进首批与不再要求是两件事。
- **审计只记结果（切到了哪个 Deployment）。** 那样的记录无法回答「为什么」，而退出条件要的是可解释。依据不记，事后就只能靠人回忆。
