# 0013 M4 二次评审

- 状态：已接受
- 日期：2026-09-11
- 阶段：M4 Match Beta（目标版本 `v0.4`）
- 前置：[ADR 0011](0011-m4-milestone-review.md) 在 2026-09-10 判定不关闭；[ADR 0012](0012-region-is-the-wrong-requirement.md) 移除了「区域」
- 结论：**仍不关闭**，但阻塞从三项收敛到一项外部依赖加两项内部缺陷

ADR 0011 是 9 月 10 日那个时点的判断，本记录不修改它。一天之内变了两件事：Hub 交付了 12H，以及把流程真正跑起来暴露了两个此前看不见的缺陷。

## 1. 退出条件是否全部满足

| 退出条件 | 结论 | 与 ADR 0011 相比 |
| --- | --- | --- |
| 相同输入和规则版本产生可重复结果 | **满足** | 不变 |
| 每个推荐都有分项理由、备选和排除原因 | **满足** | 不变 |
| 用户可以强制模型白名单、预算和隐私约束 | **未满足** | 由三缺两变为三缺半 |
| 不存在隐藏商业评分项 | **满足** | 不变 |

第三条逐项：

| 分项 | 状态 | 变化 |
| --- | --- | --- |
| 模型白名单 | 已实现 | 不变 |
| 预算 | **已实现且可用** | **Hub 交付 12H**：46 个 Deployment 中 34 个给出真实价格、5 个零价、7 个显式 `null`。`--max-price 1.0` 实测留下 2 个候选、`0.5` 留下 1 个——不再是「设了就清空」 |
| 区域 | — | 已按 [ADR 0012](0012-region-is-the-wrong-requirement.md) 移出退出条件 |
| 隐私 | 一半已实现 | 不变。发布方可过滤（`--exclude-publisher`），**实际运行请求的运营方仍不可表达**（需求 12J） |

**仍不关闭。** 把发布方过滤说成「隐私约束已满足」，正是 [ADR 0010](0010-m4-constraint-exit-condition-status.md) 决策 1 禁止的「把部分可用说成满足」——按那份记录自己的话，只有运营方那一半能回答合规问题。

12J 现在是这条退出条件**唯一的外部依赖**。

## 2. 哪些风险被验证或推翻

**新证伪的：**

- **「给对方留选择」意味着必须实现对方可能选的每一个。** 12H 的原文给了 Hub 两条路：真实售价，或用 `null` 明确表示不提供价格。Hub 两条都走了，而我们只实现了第一条——于是**第一个 `null` 让整份目录解析失败，`models`、`recommend`、`connect`、`run` 全线不可用**。需求是我们自己写的，可接受形状也是我们自己列的，却没有按自己列的形状去实现。

**新验证的：**

- **「没有度量来源的分项整项丢弃、不给零分」是对的。** 12H 交付后 `cost` 第一次真的参与排序，权重从 `compatibility 0.67 / context 0.33` 重新分配为 `0.50 / 0.33 / 0.17`，OpenCode 的第一名由 GLM-5.1 变为 DeepSeek-V4-Pro-0813。如果当初给零价打了零分，这个变化会被一个假分数掩盖，没人看得出排序依据换了。

**新暴露的两处缺陷：**

- **launcher 会静默把请求送到别处。** `run opencode` 全程报成功、Agent 答出了预期文本，而台账显示那两次请求记在一枚**预先存在的长期 key**（`myopencode`）名下、用的是 `glm-5.2`，而 Connect 刚签发的凭据零请求。已加对账检查（失败时 `LAUNCH_ATTRIBUTION_MISMATCH`），但**根因未查实**：OpenCode 为何不加载我们写入的 provider，以及它从哪里取到那枚 key。M5 的退出条件「用户始终能看到实际 Deployment 和计费主体」在这条路径上今天不成立；
- **Recommendation 的有效期没有把价格算进去。** `expiresAt` 取所引用 Evidence 里最早的到期时间（约 30 天）。但目录现在有**分时价格**：4 个 Deployment 的价格一天内翻倍（`0.22 ↔ 0.44`、`0.15 ↔ 0.3`），18 个声明 `variesBy`，Hub 也已给出 `priceValidUntil`。当前排第一的 DeepSeek-V4-Pro-0813 的 `priceValidUntil` 是 `2026-09-11T22:00:00Z`——**六个多小时后它的价格翻倍，而我们发出的推荐声称自己还有二十多天有效。** 我们已经解析了价格却没解析它的有效期。

## 3. 是否有真实用户完成核心流程

**仍无外部用户**，但闭环比 ADR 0011 时前进了：

- `[新]` `recommend → connect → verify --live → restore` 已现网跑通（ADR 0011 第 3 问点名的缺口）；
- `[新]` `switch` 链路已实测，包括**恢复时重新签发的凭据真实可用**——这条自 2026-09-05 起只有契约测试覆盖；
- `[新]` **launcher 路径实测不通过**（见上）。这是唯一一条「用户真的用起来」的入口，因此不能说核心流程已经走通；
- `[不变]` 没有人验证过排第一的 Deployment **用起来确实更好**。那需要 Scenario Quality Pack。

## 4. 下一阶段的最大未决依赖

1. **12J（运营方身份或等价的可执行约束）。** 唯一卡住退出条件的外部依赖；
2. **launcher 错配的根因。** 对账检查能让它不再静默，但不能让它正确；
3. **`expiresAt` 未计入价格有效期。** 内部缺陷，修法明确：把参与排序的候选的 `priceValidUntil` 一并纳入取最早值；
4. **macOS 无实机。** 自 M2 挂到现在，不变；
5. **Scenario Quality Pack。** 路线图那五个权重分项里，`cost` 已经活了，其余四个不变。

## 5. 是否需要缩小而不是扩大范围

**保持收窄。** `cost` 通了不是扩大范围的理由——它恰恰说明一个分项从「有数据」到「进入排序」需要多少配套（解析、零值语义、有效期、约束语义），而另外四个分项一个都还没走到第一步。

关闭 M4 需要三件，比 ADR 0011 时少一件：

1. Hub 交付 12J，Connect 据此实现运营方隐私约束并实测；
2. 修 `expiresAt` 的价格有效期；
3. launcher 的错配至少定位到根因——**对账检查使它不再静默，但一条「用户真的用起来」的入口处于已知错误状态时，不应宣布「能推荐」这个里程碑完成**。

## 需要单独决定的一件

**零价现在应当读作「免费」吗？** 12H 提出时，`0` 与「免费」不可分辨，所以 `recommend` 把零价判为「没有价格」。现在 Hub 用 `null` 承担「不提供价格」，`0` 就腾出了明确含义。现网 5 个零价 Deployment 中有一个叫 `Cohere: North Mini Code (free)`——名字自己说了。

改动很小（零价按 `0` 参与 `cost` 打分，得满分），但它会让五个 Deployment 的成本分从「整项丢弃」变成「最优」，属于排序语义变更，不在本记录中自行决定。

**已决定（同日）：零就是免费。** 依据是 `null` 已经接管了「不提供价格」这个含义，零因此不再有歧义。负数与解析不出的值仍然按「没有价格」处理——它们都不是任何人能据以排序的陈述。当前可见排名不变：现网 5 个零价 Deployment 都还没有能力证据，因此本来就不进排序；这条改动在它们被采集之后才会显现。
