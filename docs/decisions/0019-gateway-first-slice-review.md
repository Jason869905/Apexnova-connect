# 0019 Gateway 首个切片评审

- 状态：已接受
- 日期：2026-09-12
- 阶段：M5 Reliable Provider Routing（目标版本 `v1.0`）
- 前置：[ADR 0018](0018-gateway-first-slice.md) 把首个切片定为忠实转发与逐请求归属
- 结论：**四个验收目标达成，但忠实性是用较弱的方式证明的**；Gateway 仍为可选，不推荐默认启用

## 1. 四个验收目标

| 目标 | 结论 | 依据 |
| --- | --- | --- |
| 忠实 | **达成（证据较弱）** | 单元测试断言流式事件逐字节与顺序一致、上游错误按原状态码/头/体返回、只丢 hop-by-hop 头；现网 OpenCode、Codex、Hermes 经 Gateway 各返回预期文本。**但 [ADR 0018](0018-gateway-first-slice.md) 提出的那条更强的证明没有做**：用能力套件的离线回放夹具对比「经与不经 Gateway」的观察结果。见第 3 节 |
| 精确归属 | **达成** | 审计记录 `method: "gateway"`，带上游给出的 `requestId`；与直连的 `ledger-window`、`verify` 的 `request-id` 在记录与输出里都分得开 |
| 凭据不外泄 | **达成** | Agent 环境里是本地令牌，测试断言其中不含 runtime secret；Gateway 仅监听回环，令牌按常数时间比较 |
| 失败如实 | **达成** | 上游不可达时单元测试断言只尝试一次并以 502 如实返回；Hermes 的 11～12 次被拒请求全部照实计数，没有任何一次由我们重放 |

## 2. 决策事后是否站得住

- **先做转发、不做路由**（[ADR 0018](0018-gateway-first-slice.md) 决策 1、2）：站得住，而且比预想更有价值。Hermes 的协议错配是**既有缺陷**，Gateway 把它变成「11 个被拒请求，逐个点名」，而直连把同一次全败的运行报成「已确认计费 2 次」。如果首批同时引入路由选择，这个现象会被归因困难淹没；
- **不重试**（决策 5）：站得住。Hermes 自己重试了十余次，全部被拒；如果 Gateway 也重试，同一个错误会被放大一个量级，而这正是「工具副作用请求不得自动重放」要防的形状；
- **默认不开**（决策 7）：**这一条是本切片最有价值的决定**。开发过程中我自己写出的三个缺陷都只在真实运行时暴露，而直连路径始终可用，因此每次都能立刻退回去。若默认启用，这三个缺陷会先落到用户身上。

## 3. 没有做到的

- ~~**忠实性没有用最强的证据证明。**~~ **已补（同日）**：能力套件对同一份回放夹具跑两遍——一次直接打、一次经 Gateway——**逐项判定相同**。套件正是为了察觉流式顺序、取消与错误语义而造的，所以它比「三个 Agent 都返回了预期文本」强得多。

  两处必须写明的边界：**`auth.endpoint-reachable` 无法经 Gateway 提问**——那条探针检查的是「错误的凭据会被拒绝」，而 Gateway 会把调用方发来的凭据换成自己的。Agent 在 Gateway 之后**根本无法出示一个错的 Hub 凭据**，这正是那道进程边界的意义，也因此这一条按构造被排除，不是为了让测试变绿。其次，回放返回的是完整响应体，**块与块之间的真实时序没有被重现**，所以这条证明覆盖顺序与边界，不覆盖时序；
- ~~**Gateway 自身没有失败注入。**~~ **已补（同日）**：上游不回响应头、流式中途断裂、客户端中途离开、以及长流不被误杀，四条各有注入验收；
- ~~**没有超时。**~~ **已补（同日）**：超时只管到响应头（默认 60 秒），流式开始之后不设限——模型慢是它在工作，掐掉它就是截断一个真实答案。超时返回 504 且 `retryable: false`，只尝试一次；
- **没有并发验收。** Hermes 一次运行转发了 11 个请求，但是否并发未确认；多个请求同时在途时的行为没有测过；
- **凭据在运行期内不续期。** Gateway 启动时绑定的凭据用到运行结束，长会话跨过到期时间会失败，且失败形式未知；
- ~~**`path` 与 `durationMs` 采集了但没有写进审计。**~~ **已补（同日）**，但本条当初的措辞要更正：说它是「Operational Evidence 最便宜的一块」**是错的**。网关记的是单次墙钟耗时，没有聚合、没有分位数、没有测量条件，而 [`compatibility-evidence.md`](../compatibility-evidence.md) 对 Operational Evidence 的要求恰恰是这三样加上远更短的 TTL。它现在按其真实身份记录：**这条路由的逐请求明细**，schema 与输出都标明不得当作延迟测量读；
- **Claude Code 的 launcher 仍未验证**，原因不变：它的配置就是本会话在用的文件。

## 4. 一个应当被当作模式对待的失败

M5 至今出现了**三次同一形状的缺陷**：

| 位置 | 表现 |
| --- | --- |
| `--max-price` | 设了上限，一个候选都没排除，输出仍像「已按预算筛过」 |
| `restore --yes`（无事务 id） | 请求了恢复、批准了恢复，打印一张表并返回成功，配置与凭据原封不动 |
| `run --gateway` | 已有绑定时整条 Gateway 路径被跳过，请求直连发出，命令报成功 |

三次都是**开关被设置、什么也没做、并且报告成功**。三次都不是测试发现的，都是真实运行时撞出来的。

因此本记录提出一条做法上的要求：**任何「被要求却没有生效」的路径都必须失败，而不是回落**。`run --gateway` 现在已经这样做（`GATEWAY_NOT_STARTED`）。其余开关应逐个按这条复核，这属于下一批。

## 5. 是否有真实用户完成核心流程

没有外部用户。另外要写明一条限制：**所有经 Gateway 的实跑都是一次性提示**（`-z`、`exec`、`run "…"`），**没有一次是长时间交互会话**。流式稳定性、长连接、会话中途的凭据到期都因此未被触碰，而那恰是 Gateway 最可能出问题的场景。

## 6. 下一批

按影响排序：

1. **Gateway 的失败注入与超时**——它现在在请求路径上，而路径上的组件没有失败验收；
2. **忠实性的强证据**——用回放夹具做经/不经 Gateway 的逐事件对比；
3. **把 `path` 与 `durationMs` 写进审计**——延迟数据已经在手边，这是 Operational Evidence 最便宜的一块；
4. **一次长会话实跑**；
5. 之后才谈 Circuit Breaker 与受控选择。

**不建议**在第 1、2 条完成前把 Gateway 设为默认。它今天能用，但"能用"与"路径上的组件"是两个标准。
