# 0008 非 Apexnova Provider 的候选来源属于 M5

- 状态：已接受
- 日期：2026-09-10
- 阶段：M4 Match Beta（目标版本 `v0.4`）
- 前置：[ADR 0007](0007-m4-scope-and-recommendation-path.md) 决策 2 把这条挂账，并要求在 M4 中期在三个选项里做出选择

## 背景

路线图给 M4 的退出条件之一是「允许推荐非 Apexnova Provider」。ADR 0007 决策 2 首批不引入第二候选来源，把这条明确挂账，并留下三个选项：引入本地 Ollama、引入用户自带 endpoint，或者承认它属于 M5。本记录做这个选择。

挂账时的理由是「现在没有第二个来源」。这一条今天仍然成立，但它不足以做决定——真正决定形状的是**引入一个候选之后会发生什么**。三处代码给出了答案。

### 1. 候选注入这一侧确实是通的

`packages/recommendation` 不 import 目录客户端：`recommend()` 接收 `candidates` 数组，候选的形状是 `deploymentId`、`displayName`、`protocols`、`availability`、可选的 `pricing`、`contextWindow` 与 `implementationFingerprint`。ADR 0007 决策 2 承诺的可插拔是真的，不是纸面上的。

因此**第二来源的成本不在推荐引擎里**。这也意味着推迟它不会积累架构债：引擎不需要为此改形状。

### 2. 但候选拿不到证据，而没有证据的候选只会出现在排除列表里

`collectEvidence()`（`apps/cli/src/run-cli.ts`）在五个点上是 Hub 形状的：

- 目录解析出 Deployment 与 `inferenceAlias`；
- `createRuntimeCredential` 签发只对这一个 Deployment 生效的临时凭据；
- 端点取自目录的 `hubProtocol.baseUrl`；
- 预算上限对的是 Hub 的估价响应；
- 事后按 Hub 的 `requestId` 逐条对账，并撤销凭据。

一个本地 Ollama 或用户自带 endpoint 五条都不满足：没有目录条目、没有可签发的 runtime credential、没有估价、没有计费台账可对。

而按 ADR 0007 决策 4，required 能力没有实测证据的候选 `eligible: false`。**所以在没有第二条采集路径的前提下引入第二候选来源，产出的是一批永远排在「Excluded」里的行**——看起来支持了非 Apexnova Provider，实际一条也推荐不出来。这正是 M3 全程守的那条规则的反面：不得把没测过的东西显示成别的样子。

### 3. Recommendation 的来源字段今天只能描述一个来源

`RecommendOptions.catalogVersion` 是必填的单值，并被记进每条 Recommendation，用于 ADR 0007 决策 6 的可重复性。候选一旦来自两个来源，这个字段就不再说明「候选是从哪里来的」——本地 Ollama 的模型列表没有 `catalogVersion`，而同一条 Recommendation 又必须能被重算。这需要把来源与版本一起改成逐候选的信息，是一处真实的契约改动，不是加一个数组。

## 决策

1. **M4 不引入第二候选来源。** 三个选项里选「承认它属于 M5」。

2. **这条退出条件从 M4 移到 M5，并且是移动，不是删除。** 它的措辞、要求和验证标准都不降低。M4 收口时不把它记成「已满足」，也不再把它记成「M4 未满足的一条」——它不再是 M4 的退出条件。

3. **移动的理由必须是结构性的，不能是「没做完」。** 依据是上面第 2、3 两条：这条退出条件真正需要的不是第二个候选**列表**，而是第二条**证据采集路径**加上逐候选的来源记录。前者是 M5「本地 Gateway 与 Hub 路由协作」的同一件事——两者都要求 Connect 能对一个不由 Hub 签发凭据、不由 Hub 计费的端点说话。放在 M4 会先造出一个只能排除、不能推荐的假支持。

4. **在此之前，`recommend` 必须说清楚候选只来自 Apexnova 目录。** 这是一条对用户的陈述，不是文档脚注：不写出来，一份只有 Apexnova Deployment 的排行看起来就像是「全市场里最好的四个」。

5. **推荐引擎保持候选注入的形状，不为此改动。** 依据是第 1 条：这一侧已经是通的，M5 引入第二来源时不需要重构引擎。

## 后果

- M4 的退出条件从五条变为四条；M5 增加一条，并在范围里说明它依赖的是采集路径而不是候选列表；
- M4 收口（未来的 ADR）不再需要为这条写「未满足」；相应地，**M5 收口时不能以「M4 已经推迟过一次」为由再推迟一次**——推迟的理由已经用掉了；
- 「不存在隐藏商业评分项」这条退出条件不受影响：候选只来自一个来源，与 `sponsored` 是否参与排序无关，后者由 ADR 0007 决策 8 的断言测试保证；
- 首批推荐的适用范围因此是明确且有限的：Apexnova 目录内的排序。这是诚实的窄。

## 被否决的选项

- **引入本地 Ollama 作为第二来源。** 采集路径不通（背景 2），产出的候选只能被排除。而且 Ollama 的模型没有 `implementationFingerprint`，subject 身份里那一格会长期为空——M3 花了整个阶段把它填上，不应在 M4 主动引入一批填不上的。
- **引入用户自带 endpoint。** 同上，另加一条：用户自带 endpoint 的凭据不由 Hub 签发，Connect 需要一套自己的凭据边界与撤销语义。那是 M5 的问题，不是候选来源的问题。
- **保留在 M4，收口时记为未满足。** ADR 0007 的原定兜底。它对「没来得及做」是对的，对「结构上不属于这里」是错的——把一条属于别处的条件挂在 M4 上，只会让 M4 的收口记录多一行永远解释不掉的未满足。
- **降低这条退出条件的要求，例如改成「架构上允许」。** 引擎接收候选数组这件事今天就成立，改成这个措辞等于宣布它已经满足。那是把措辞改到现状上，不是满足要求。
