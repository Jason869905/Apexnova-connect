# 0005 M3 里程碑评审

- 状态：已接受
- 日期：2026-09-08
- 阶段：M3 Compatibility Beta（目标版本 `v0.3`）
- 后续：本记录的「不宣布关闭」结论已由 [ADR 0006](0006-m3-closure.md) 更新（2026-09-09 收口）。本文不修改，它记的是 9 月 8 日那个时点的判断

路线图要求每个里程碑结束时记录一份 Decision Record，回答五个问题。以下按顺序回答。

## 1. 退出条件是否全部满足

| 退出条件 | 结论 | 依据 |
| --- | --- | --- |
| 每个公开 Verdict 都有可追溯 Evidence | **满足** | [兼容性矩阵](../compatibility-matrix.md) 由 `compatibility matrix` 从证据生成，逐行列出所依据的 Evidence ID；此前手写的那张表已被生成物取代 |
| Vendor Claimed 与 Apexnova Verified 分开 | **满足** | `provider-claim` 记录单独存储，永远不产生 `supported`；只有声明时能力读作 untested，更新的声明也覆盖不掉更早的实测 |
| 测试可在隔离环境中重放 | **满足** | `--record` / `compatibility replay`；仓库内保留一份对现网 `qwen3.8-flash` 的真实运行录制，回放逐项复现当时的八个结论 |
| 模型、Provider、Integration 或 Test Suite 版本变化会使相关 Evidence 过期 | **未满足（Provider 维度）** | Agent 版本、Integration 版本、Deployment、协议、平台任一变化都不匹配 subject；测试套件 major 变化使旧记录不再支撑 Verdict；TTL 逐 statement 生效。但**上游供应线路变化无法感知**——目录不暴露上游身份，也没有实现指纹（见 [12A.5(a)](../apexnova-ai-hub-requirements.md)） |
| 失败日志完成脱敏 | **满足** | 探针只记结构性描述并截断；录制不记请求头、响应头走白名单、内容过脱敏；Evidence 落盘前做凭据模式检查。三处都有断言测试 |

范围交付物中，`Hub Evidence 查询接口` 未交付（跨仓依赖，需求见 12A）；能力测试按 [ADR 0004](0004-m3-scope-and-evidence-path.md) 收窄为 8 项，图片、缓存、长上下文与并行 Tool Call 明确推迟到第二批。

M3 因此**不宣布关闭**，处理方式与 M2 一致：除依赖 Hub 的部分外全部满足，不通过降低验证要求把它标记为通过。具体地，建议在 12A 的 (b)(d) 落地并完成一次真实同步之前保持开启——「公开」这件事目前还没有服务端支撑。

## 2. 哪些风险被验证或推翻

**被推翻的**

- *「目录声明可以当作能力事实」*。`openai-responses` 路径上 4 个 Deployment 全部忽略 `text.format.json_schema` 且不报错，其中 `deepseek-v4-pro-0813` 与 `qwen3.8-flash` 在目录里明确声明了 `structured-output.json`。同一批模型在 `anthropic-messages` 上用 tool 承载 schema 则 3/4 通过。ADR 0004 决策 8 写下的假设在第一批就兑现了。
- *「一次观测就是一个属性」*。GLM-5.2 在 `anthropic-messages` 上的 Tool Call、结构化输出与无效请求首轮全部 502，17 分钟后重跑得到 8/8 `compatible`。瞬时故障与稳定缺陷只能靠重复观测区分——这正是不可变记录加时间序的用处，也说明单次采集不足以支撑公开结论。
- *「探针越严格越好」*。`agent.single-tool-call` 原本发送强制 `tool_choice`，把「模型能否调用工具」测成了「端点是否接受强制指定工具」，`qwen3.8-flash` 因此被误记为不支持 Tool Call。**测试断言必须与能力定义等价，不能更强**，否则产出的是关于探针的结论。

**被验证的**

- 本地先行、后同步（ADR 0004 决策 5）是对的。M3 全程没有被 Hub 阻塞，而 12A 的接口需求是由 12 轮真实记录反推出来的，不是凭空设计的契约。
- 收窄到 2 Agent × 4 Deployment × 8 项测试是对的。这个规模就已经暴露了 7 个服务端缺口和 3 个 Connect 自身的缺陷；按路线图原定的 3 × 6～10 铺开，成本与噪音会先于结论到来。
- 不可变加 `supersedes` 经得起真实使用。两次纠正（GLM-5.2 的 502、qwen 的 tool_choice 误判）都是靠写新记录完成的，没有删改任何历史。

**新暴露的**

- 计费对账无法在运行结束时一次完成。Hub 结算滞后于响应，首次实现因此把未结算显示成 `Billed: 0.000000 USD`——本地数字被当成实际费用，正是 M1 明令禁止的错误，而且那个数字已经写进了不可变记录。已修正为重试后如实区分「已结算/未结算」。
- 传输层错误曾被当成对被测端点的结论。回放缺口会被记成 `unsupported`，即用陈旧录制生成关于 Deployment 的「发现」。已修正为让 `CapabilityError` 穿透。
- 被客户端中断的流式请求，计费不一致：12 轮里 11 轮在用量里查不到（数小时后仍然查不到），1 轮正常计费。

## 3. 是否有真实用户完成核心流程

有。维护者在现网 Hub（`api.apexnova-consulting.com`）完成 12 轮真实采集，覆盖 4 个 Deployment × 2 个 Agent，合计实扣 `0.009016 USD`，全部按 requestId 与 Hub 用量逐条对账。产物是 8 条 subject 的公开矩阵、一份可回放的真实录制，以及 12A 里七条由此得出的服务端需求。

尚无外部用户完成该流程。

## 4. 下一阶段的最大未决依赖

- **Hub 的 Evidence 接口（12A）**。其中 (b) 推理错误响应缺少 Request ID 与 (d) 用量查询无法区分「未结算」与「不计费」是硬前置：不修好，对账与追踪在服务端同样不成立。
- **上游 Provider 身份或实现指纹（12A.5(a)）**。它直接决定「Provider 变化使 Evidence 过期」这条退出条件能否满足；在此之前，公开矩阵对上游变更是盲的。
- **macOS 实机**。M2 遗留至今未解决，现在同时阻塞该平台的 Evidence 采集——矩阵里没有也不可能有 macOS 行。

## 5. 是否需要缩小而不是扩大范围

M3 期间范围没有扩大，反而按 ADR 0004 主动收窄了一次，事后看这次收窄直接决定了成败：11 轮采集里有 3 轮是用来纠正前面结论的，如果第一批是 30 轮，纠正成本会高一个量级。

进入 M4 建议同样从最小规模起步：Coding Scenario Pack v1 先固定 1 个 Scenario 与少量任务，跑通「可重复、可解释、有 Evidence 支撑」的闭环之后再扩。M3 已经证明，规模会先于结论成为瓶颈。

M3 自身的第二批（图片、缓存、长上下文、并行 Tool Call，以及第三、第四个 Agent 和更多 Deployment）应当**等 12A 就绪之后**再扩：现在扩只会积累更多无法发布、无法按上游变更过期的本地记录。
