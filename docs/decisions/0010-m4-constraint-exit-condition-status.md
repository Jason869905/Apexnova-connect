# 0010 M4 约束退出条件的逐项状态

- 状态：已接受
- 日期：2026-09-10
- 阶段：M4 Match Beta（目标版本 `v0.4`）
- 性质：记录，不是变更。本记录不移动、不改写、不降低任何退出条件

## 背景

路线图给 M4 的退出条件之一是「用户可以强制模型白名单、预算、区域和隐私约束」。四项分别处在四种不同的状态，此前被当作一件事对待，因此没人说得出它满足到什么程度。本记录把四项拆开，逐项写下今天的事实与依据，为 M4 收口留下可核对的底账。

M0 的 CLI 规格为 `recommend` 预留过 `--priority`、`--region`、`--provider`、`--model-allowlist`、`--verified-only`，[`cli-spec.md`](../cli-spec.md) 记为「首批都未实现」。那句话是对的，但给出的理由有一处过强，见下面第 4 项。

## 逐项状态（2026-09-10 对现网目录核对）

### 1. 预算：接口存在，但今天**静默无效**

`recommend --max-price <每百万>` 存在，语义是**混合单价上限**（按 `coding.v1` 的 0.75/0.25 输入输出比折算），不是花费上限——花费上限是 `compatibility run --budget` 那条，两者不要混。

过滤条件是 `blended !== undefined && blended > ceiling`：**没有可用价格的候选直接通过**。而目录当前对全部 Deployment 发布 `pricing: 0`（需求 12H），`recommend` 按既定规则把零价读作「没有价格」，于是每一个候选都落进那个 `undefined` 分支。

实测：`recommend claude-code --max-price 0.000001` 仍然返回 4 个 eligible。**用户明确设置的约束一个候选都没排除，输出里也没有一句话说它没起作用。** 输出确实有一行「Not measured — cost: 目录没有可用价格」，但那是在说分项不参与排序，不是在说「你给的上限被忽略了」。

这与 M3 全程守的规则是同一条：不得把「没测过」显示成「支持」。一个静默匹配全部候选的约束，显示的是「已按你的预算筛过」，而实际上没有。**这条是缺陷，不是未实现**，处置见下面的决策 2。

### 2. 模型白名单：引擎侧已具备，CLI 侧只开了单数

`RecommendationConstraints.deploymentIds` 本来就是数组，过滤逻辑按数组写的。CLI 只暴露单个 `--deployment <id>`，传进去时包成 `[parsed.deployment]`。

因此「白名单」缺的是命令行入口，不是能力。目录另有 `modelId` 与 `aliases`，按模型（而不是按 deployment）做白名单同样有数据支撑。**可实现，成本小。**

### 3. 区域：目录里没有任何区域字段

`HubCatalogDeployment` 没有区域属性，现网 46 个 Deployment 的原始 JSON 里也没有任何区域信息。区域约束**在当前目录下不可实现**，且不是 Connect 侧能补的：需要 Hub 在目录里发布它。

### 4. 隐私：一半有数据，一半没有——ADR 0007 那句话过强

[ADR 0007](0007-m4-scope-and-recommendation-path.md) 决策 3 把 `privacy` 记为未测量，理由是「需要上游 Provider 身份，目录只给不可逆指纹」。**「只给不可逆指纹」这个说法过强，本记录予以更正**：

- **实际运行模型的上游运营方，目录确实不给。** 46 个 Deployment 的 `providerId` 全部是 `provider.apexnova-ai-hub`，`kind: "platform"`；`providers` 数组里只有这一个条目。以「不要让某运营方看到我的代码」表达的隐私约束，今天无从表达，也无从校验；
- **但模型的发布方，目录给了。** `model.publisher` / `publisherName` 存在且已被解析器读入，现网 46 个 Deployment 覆盖 12 个发布方（Anthropic 5、Qwen 10、ByteDance 6、DeepSeek 5、Zhipu AI 4、OpenAI 4、NVIDIA 4、Google 3、Moonshot AI 2，Cohere / xAI / MiniMax 各 1）。以「不要用某发布方的模型」表达的隐私或合规约束，**今天就能实现**。

两者是不同的问题，混成一句「隐私无从区分」会把能做的那一半也一并埋掉。`privacy` 作为**打分分项**仍然不参与排序（发布方身份不能度量隐私强度）；作为**硬约束过滤**，发布方这一维是可用的。

### 5. 顺带核对：`--verified-only` 确实没有意义

cli-spec 的说法成立：没有实测证据的 Deployment 本来就 `eligible: false`，所以「只看已验证的」是当前默认行为，加一个开关只会让人以为存在一种「不验证也推荐」的模式。

## 决策

1. **本记录不改动任何退出条件。** 四项的去留在 M4 收口时按 [ADR 0006](0006-m3-closure.md) 的做法一并判断，依据就是上面的逐项事实。在此之前，不把「部分可用」说成满足，也不把「目录没有」说成 Connect 未做。

2. **第 1 项（预算静默无效）按缺陷处理，优先于其余三项。** 一个被设置却什么也没做的约束，比一个没有实现的约束更糟：后者会报错，前者会让人以为筛过了。修法的方向是让无价候选在有上限时无法静默通过——要么排除并说明「价格未知，无法证明它在预算内」，要么保留但在输出里明说该上限对本轮没有约束力。两者都是决定，不是实现细节，因此单独提出。

3. **第 2 项（白名单）与第 4 项的发布方过滤属于可实现范围**，成本小，但本记录不预先承诺它们进入 M4——那取决于 M4 收口时的范围判断。

4. **第 3 项（区域）与第 4 项的上游运营方身份记为「依赖 Hub」**，与 [ADR 0008](0008-non-apexnova-candidates-belong-to-m5.md) 移到 M5 的那条同源：都卡在目录只发布单一 platform Provider 这一点上。若 M4 收口时仍无数据，如实记为未满足，不降低要求。

## 后果

- M4 收口时这条退出条件有底账可查，不需要再临时判断「算不算满足」；
- ADR 0007 决策 3 关于 `privacy` 的理由被本记录更正一处：目录给出模型发布方，不给出上游运营方。该分项不参与排序的结论不变，理由改为「发布方身份不能度量隐私强度」；
- `cli-spec.md` 中「区域与 Provider 在只有一个公共 Provider、且目录只给不可逆指纹的前提下无从区分」一句同步更正。
