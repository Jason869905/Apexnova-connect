# 0021 经 Gateway 的凭据在运行期内续期，并且一律是短期的

- 状态：已接受
- 日期：2026-09-12
- 阶段：M5 Reliable Provider Routing（目标版本 `v1.0`）
- 前置：[ADR 0020](0020-gateway-batch-closure.md) 把「运行期内凭据不续期」记为**未实现**，并列为 Gateway 转默认的第 1 个条件
- 结论：续期已实现；`--gateway` 改为一律签发 24 小时短期凭据。**顺带更正 ADR 0019 与 0020 的一处事实错误**

## 1. 先更正一条：默认路径上根本没有到期这回事

ADR 0019 写「长会话跨过到期时间会失败」，ADR 0020 把它加重成「一次跨过 24 小时 TTL 的运行**会**失败」。**这对默认路径不成立。**

`run` 默认签发的是**永不过期的用户 key**（`POST /v1/api-keys`，`expiresIn: null`），只有 `--rotating` 或走 `connect` 才拿 24 小时的运行时凭据。而 `run --gateway` 此前走的正是默认那条。所以那句话描述的是一条当时**没有人走**的路径。

我在 ADR 0020 里把它从「未验证」改判为「未实现」时，核对的是绑定赋值几次，没有核对签发的是哪一种凭据。改判的方向是对的，论据只对了一半。

## 2. 决策：`--gateway` 蕴含短期凭据

`run` 默认发永久 key 有一个具体理由：**直连时凭据在 Agent 自己的配置文件里**，换一枚意味着在 Agent 已经读过之后改写那份文件。那不是续期，那是在一个运行中的进程底下抽掉它的输入。

**经 Gateway 时这个理由不成立**：Agent 拿到的是本地令牌，Hub 凭据从没离开过 CLI 进程。换一枚凭据在进程边界的这一侧完成，Agent 无从察觉。

两条后果，方向一致：

- 唯一挡住短期凭据的理由消失了；
- 短期凭据同时收窄了崩溃的后果。这条路径本来就在运行结束时收回自己的凭据；**如果它没走到那一步**，留下的是一枚 24 小时后自己失效的凭据，而不是一枚永久的。

**代价要写明**：`run --gateway` 现在每次都会向 Hub 签发一枚新凭据，而此前复用永久 key。这对签发量是实打实的增加，也意味着 Hub 侧的凭据列表会更热闹。接受它，因为上面第二条后果更重要。

## 3. 续期的形状

- **在请求到来时触发，不用定时器。** Gateway 本来就每个请求读一次凭据（这是为了让它能在凭据存在之前就开始监听）。同一个读现在也承担续期：剩余不足 1 小时就先换再转发；
- **同时到期的多个请求只换一次。** 轮换本身有跨进程文件锁并在锁内复检，所以重复尝试**不会多签发**——它们会各自在锁上排一次队（100ms 重试间隔）。共用一次续期挡掉的是排队，不是多签。**这两件事此前被我混为一谈**，测试的注释里写明了区别；
- **续期失败不中断运行。** 「到期」指剩余不足 1 小时，不是已经失效，手上这枚仍然可用。运行继续并给出警告；真到期之后 Hub 返回 401，Gateway 原样透传——那是实际发生的事，好过在这里替上游猜一个错误。失败后有 60 秒冷却，否则一次 Hub 故障会被每个转发请求各问一遍，把对方的故障放大成我们自己的；
- **归属按凭据拆分。** 一次跨过续期的运行由两枚凭据分别付账，因此 `ForwardedRequest` 逐请求记下是哪一枚，审计的 `billedTo` 按凭据分行。之前那种「整轮一个总数」会把前一段的请求记在一枚从没为它付过账的凭据上。计费对账用的 `attributeLaunch` 同理改为接受一个凭据集合，否则续期后的请求会被算成**别人的**。

## 4. 对 ADR 0020 转默认条件的影响

第 1 条（凭据可续期）的**实现部分**完成。但那一条原文要求的是「可续期**并且有一次跨过到期时间的实跑**」，而这里交付的是实现与四条验收，**不是实跑**：所有验证都在受控时钟下完成，真实的 24 小时会话一次都没发生过。

**因此第 1 条不算满足，Gateway 仍不转默认。** 这一批恰好又证明了为什么：本条记录开头更正的那个事实错误，是在写测试、发现续期从不触发时才暴露的——距离它被当作确定结论写进两份 ADR 已经过去一整轮。
